# 概要｜LLM を用いた質的コーディングのためのパイロット手順

*本編は英語です → [README.md](README.md)　／　失敗パターンの詳細 → [PITFALLS.md](PITFALLS.md)*

数千件の文書を複数の観点で分類する作業は、人手では終わりません。LLM なら終わります。問題は、**その結果を信頼してよいか** です。

本リポジトリの提案は、本番の前に **パイロット** を行い、「再現可能であることを示せる手引き（コードブック）」を作ることです。研究者と AI が一致するだけでは不十分で、**手引きの文面だけを渡された第三者が、同じように分類できる** ことを確認します。

## 手順

### 第 1 部　パイロット

| 段階 | 内容 |
|---|---|
| **0　抽出と留保** | 資料の種類ごとに層別抽出し、**作業を始める前に 3 分の 1 を文書単位で取り分ける**。最後まで開かない。合格基準もここで決める |
| **1　初版の作成** | 理論から分類の観点と値を設定する。各値について「その証拠は何か」を確認し、「証拠なし」に当たる値の欠落を防ぐ |
| **2　試行と改訂** | 初回コーダー（AI）が分類し、研究者が確認、手引きを改訂。数回繰り返す |
| **3　再現性の問題** | 研究者も初回コーダーも手引きの設計に関わっており、「意図」で読んでいる。**一貫した誤りは正しく見える**。そこで、設計に関わっていない別の AI（検証コーダー）に **手引きの文面だけ** を渡して分類させ、差分を見る |
| **4　再改訂** | 差分を 4 種類に分け、文面を意図に近づける |
| **5　最終検証** | 取り分けておいた 3 分の 1 で一度だけ測定。研究者の基準を **先に** 確定させてから比較する |

**不合格の場合の選択肢は二つ**：限界として記録して確定するか、改訂したうえで **新しい未使用データ** で再検証するか。同じデータで再検証するのは不可。

### 第 2 部　本番コーディング

役割は **研究者と初回コーダーの二者のみ**。

1. 初回コーダーが全件を分類
2. プログラムで全件を機械走査し、形式上の欠陥を先に除く（抜き取り検査では見つからない）
3. 研究者が 30% を層別に抜き取り検査
4. 不一致が **系統的** なら当該層を全件確認し手引きを改訂、**偶発的** なら個別に修正

大量処理では **約 20 件ずつ、毎回独立した文脈で** 実行します（同一セッションで続けると、AI が自分の前の回答をなぞり始めるため）。

## 一つの事例で確認されたこと

| 内容 | 結果 |
|---|---|
| 「証拠なし」に当たる値の欠落を検証コーダーが発見 | 一致率 **8.7% → 90%** |
| 同一セッションで連続実行した場合の自己収束 | 一致率 **0% → 100%**（セッションを分けただけ） |
| 分類誤りの検出：30% 抜き取り vs 全件走査 | 5 件中 **0 件** vs **5 件** |
| 一度も改訂に使っていないデータでの最終検証 | 90.5% / 71.4% / 69.8% |

最後の検証では 3 つの判定基準の不備が判明しましたが、限界として記録し、基準は修正していません。

## 根拠データの範囲

中国語の行政文書 163 件（2026 年 9 月）。初回コーダーに Claude、検証コーダーに ChatGPT・Gemini。
**手順は転用できますが、数値そのものは本事例に固有のものです。**
