# 概要｜LLM を用いたテキストコーディングの失敗パターン

*本編は英語です → [README.md](README.md)*

大量のテキストを分類する作業を LLM に行わせる場合、**単一のコーダー＋人間によるレビュー**という構成では見つけられない失敗が複数あります。レビューで検出できるのは「不統一」であり、「一貫した誤読」は検出できないためです。手引きの通りに読み、その通りに分類されていれば、誤っていても「正しい」と見えます。

本リポジトリは、その種の失敗を 7 つに整理し、それぞれについて **検出方法** と **見逃した場合の代償** を記しています。

## 確認された主な数値

| 内容 | 結果 |
|---|---|
| 分類値の設計漏れ（「証拠なし」に該当する値が存在しなかった） | 修正により一致率 **8.7% → 90%** |
| 同一セッションで連続実行した場合の自己収束 | 一致率 **0% → 100%**（セッションを分けただけ） |
| 抽出引用が隣接セルへ越境していた件数 | 163 件中 23 件 → 境界規則の導入後 0 件 |
| 抽出漏れの検出：30% 抽出検査 と 全件機械走査 の比較 | 分類誤り 5 件のうち、抽出検査 **0 件** / 機械走査 **5 件** |
| 事前に分離し一度も改訂に用いなかった 63 件での検証 | 90.5% / 71.4% / 69.8% |

最後の 63 件の検証では 3 つの判定基準の不備が判明しましたが、**いずれも修正していません**。修正すれば、唯一の独立した検証用データが失われるためです。不備は限界として記録し、基準は据え置きました。

## 対象とする読者

テキストデータの分類・ラベリングを LLM に任せる作業を行っており、その結果をどこまで信頼してよいか判断する必要がある方。

## 根拠データの範囲

中国語の行政文書 163 件（2026 年 9 月実施）。産出コーダーに Claude、独立検証に ChatGPT・Gemini を使用。
**検出方法は転用可能ですが、数値そのものは本事例に固有のものです。**
