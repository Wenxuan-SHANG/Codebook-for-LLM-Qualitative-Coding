# 第 1 部　手順

## 出発点

数千件・一億字規模の文書を、複数の観点で同時に分類したい。結果は「単位 × 観点」の表になります。

人手では終わりません。AI なら終わります。ただし AI は **何か** に従って分類しなければなりません。

すぐ思いつくのは **プロンプト** です。本手順の答えは **コードブック**（分類の手引き）です。何を一単位とするか、どんな分類があるか、各値が何を意味するかを書いた規則集です。プロンプトは出力が良く見えるまで調整するものですが、コードブックは研究の道具です。版を管理し、検証し、**書いた本人以外にも同じように使える** ことを示します。

## 記号

| 記号 | 意味 |
|---|---|
| **CB** | コードブック |
| **CB(n)** | コードブックの第 n 版 |
| **R(n)** | 第 n 回の改訂 |
| **Coding result(n)** | 第 n 版の分類結果 |

| 版 | どこで作られるか | 位置づけ |
|---|---|---|
| **CB(1)** | 段階 1、理論から | 初稿 |
| **CB(2)** ＋ 分類結果(1) | 段階 2、改訂 R(1) | 研究者と一致する |
| **CB(3)** | 段階 4、改訂 R(2) | **定稿？**　第三者とも一致するが、未見のデータでは未検証 |
| **CB(4)** | 段階 5 | **定稿** |

## 一つのループを四回まわす（甲乙丙丁）

方法全体は **「分類 → 確認 → 改訂」** という一つのループを四回まわすものです。回ごとに変わるのは **誰が確認するか** と **どのデータで行うか** で、回を追うごとに独立性が高まります。

| ループ | 位置 | 分類する者 | 確認する者 | データ | 確かめること |
|---|---|---|---|---|---|
| **甲**　R(1) | 段階 2 | 初回コーダー | 研究者 | 開発用 | 分類が研究者の意図どおりか |
| **乙**　R(2) | 段階 4 | 検証コーダー | 研究者と照合 | 開発用 | 手引きの **文面だけで** その意図が再現されるか |
| **丙** | 段階 5 で不合格の場合のみ | 検証コーダー | 研究者と照合 | **新しい** 未使用データ | 改訂版が未見のデータでも通用するか |
| **丁** | 本番 | 初回コーダー | 研究者（30% 抜き取り） | 本番データ | 本番の分類が正しいか |

## パイロット

| 段階 | 内容 | 産出物 |
|---|---|---|
| **0　留保** | 資料の種類ごとに層別抽出し、**作業前に 3 分の 1 を文書単位で取り分ける**。最後まで開かない。合格基準もここで決める | — |
| **1　理論から** | 分類の観点と値を理論から設定する（例：主張の類型、承認、採用）。各値について「その証拠は何か」を確認する | **CB(1)** |
| **2　ループ甲** | 初回コーダー（AI）が分類し、研究者が確認、改訂。数回繰り返す | **CB(2)**、分類結果(1) |
| **3　問題** | 研究者も初回コーダーも設計に関わっており、**意図** で読んでいる。一貫した誤りは見つけにくい。そこで設計に関わっていない別の AI（**検証コーダー**）に **文面だけ** を渡し、単位の切り出し・類型・値の付与を比べる | — |
| **4　ループ乙** | 差分に基づいて再改訂し、**文面を意図に近づける** | **CB(3)　定稿？** |
| **5　最終検証** | 取り分けた 3 分の 1 で、検証コーダーと研究者の基準を比較。**研究者の基準を先に確定させる** | — |

**段階 5 の結果**

- **合格** → CB(3) を **CB(4)** として確定
- **不合格** → 選択肢は二つ
  - **限界として記録** し、規則は変えない。CB(3) に限界の記録を加えたものが **CB(4)**
  - **ループ丙**：改訂したうえで、**新しい未使用データ**（本番データの一部を検証コーダーに分類させる）で再検証。合格した改訂版が **CB(4)**
  - 同じ 3 分の 1 で再検証するのは不可

## 本番コーディング

役割は **研究者と初回コーダーの二者のみ**。検証コーダーは退く。

1. 初回コーダーが CB(4) で全件を分類
2. **ループ丁**：研究者が 30% を層別に抜き取り検査
   - **系統的** な不一致 → 当該層を全件確認し、手引きを改訂
   - **偶発的** な不一致 → 個別に修正

補足：人による検査の前に、プログラムで全件を機械走査して形式上の欠陥を除く。大量処理では **約 20 件ずつ、毎回独立した文脈で**（API またはサブタスク）実行する。

# 第 2 部　7 つの落とし穴

### 1. 分類値に「証拠なし」の欄がない
「採用／一部採用／不採用」のような値は、記録に何か書かれていることを前提にしています。実際に最も多いのは **何も書かれていない** 場合で、それが「不採用」に吸収されると、沈黙が拒否に変わります。
→ 事例：「追跡可能な結果なし」を追加し、一致率 **8.7% → 90%**

### 2. 一貫した誤りは正しく見える
自分で書いた手引きで自分の分類を確認すると、同じ読み方を当てはめるので必ず一致します。人による確認は「不統一」は見つけられても、「一貫した誤読」は見つけられません。**手引きを書いていない第三者** が必要です。

### 3. 同一セッションでバッチを続けると結果が変わる
同じ会話の中で続けて分類させると、AI は規則を読み直すのではなく、**自分の前の回答をなぞり始めます**。
→ 事例：セッションを分けただけで、一致率 **0% → 100%**

### 4. 抜き取り検査では系統的な欠陥が見えない
抜き取りは「割合」を推定する道具です。技術的な欠陥は特定の書式や文書型に **集中** するため、無作為抽出では最も見落とされやすくなります。全件を機械で走査する検査を併用します。
→ 事例：分類誤り 5 件のうち、30% 抜き取りで **0 件**、全件走査で **5 件**

### 5. モデルを経由した引用は引用ではない
AI に原文を書き出させると、言い換えや省略があっても見分けられません。AI には **位置（冒頭の数十文字）だけ** を出させ、引用そのものはプログラムが原文から文字位置で切り出します。
→ 事例：隣接セルへの越境 163 件中 23 件 → 0 件

### 6. 手引きの改訂に使ったデータで手引きを検証しても何も測れない
改訂とは、規則をそのデータに合わせることです。同じデータで測れば、合わせた度合いを測っているにすぎません。**最初に取り分けたデータで一度だけ** 測ります。不合格なら、限界として記録するか、新しいデータで再検証します。
→ 事例：90.5% / 71.4% / 69.8%。限界として記録し、規則は変えず

### 7. 2 つのモデルの一致は評定者間信頼性ではない
LLM どうしは学習データの大半を共有しており、独立した判定者ではありません。一致していても同じ誤読を共有している可能性があり、人はかえって確認しなくなります。**kappa は計算せず**、役割（初回コーダー／研究者／検証コーダー）を機能で区別します。
